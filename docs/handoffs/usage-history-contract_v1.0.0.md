# 사용량 기록 API 계약 v1.0.0

작성: Claude (프론트엔드) · 2026-10-29 · 받는 쪽: Codex (백엔드·수집)

## 왜 필요한가요

사용량 맵 메뉴에 세 가지를 추가합니다.

1. **사용 히트맵**: 두 형태를 토글합니다.
   - **월간**: 날짜별 달력이며, 월 단위로 넘겨 봅니다.
   - **시간대별 (최근 30일)**: 요일 × 0~23시 표입니다.
2. **모델별 사용량 추이**: 상위 5개 모델과 기타를 누적 영역 그래프로 보여 줍니다.
3. **프로젝트별 사용량 추이**: 상위 5개 프로젝트와 기타를 같은 형태로 보여 줍니다.

지금 `/api/state`로는 이 그래프들을 그릴 수 없습니다. 이유는 세 가지입니다.

- `events`는 도구(`kind`)별 합계만 있고, 모델과 프로젝트가 없습니다.
- 기록은 수집기가 저장을 시작한 2026-10-27 15:04 이후뿐입니다.
- 긴 기간의 `events`는 기간 시작 시각 기준 최대 240개 구간으로 묶여서, 날짜·시각 경계와 맞지 않습니다.

## 요청

```
GET /api/history?period=<key>&step=<step>[&kind=<kind>]
```

| 매개변수 | 값 | 설명 |
|---|---|---|
| `period` | `/api/state`와 같은 키: `10m` `30m` `1h` `5h` `12h` `24h` `custom:<초>` `all` | 추이 그래프의 기간입니다. 화면의 기간 슬라이더 값을 그대로 보냅니다. |
| `step` | `60` `300` `900` `3600` `day` `week` | 추이 구간 크기입니다. 구간이 400개를 넘으면 `400 Bad Request`로 응답해 주세요. |
| `kind` | 선택. `Claude` `Codex` `GLM` `Aside` 등 | 사이드바 "AI별 보기" 필터입니다. 없으면 전체입니다. 추이와 히트맵 모두에 적용합니다. |

- 읽기 전용 로컬 API입니다(127.0.0.1). 원격 릴레이로 보내지 않습니다.
- 화면은 사용량 맵을 열어 둔 동안에만 요청합니다. 메뉴를 열 때, 기간이나 AI 필터를 바꿀 때, 그리고 60초마다 요청합니다.
- 응답 시간은 300ms 안을 목표로 합니다. 집계는 캐시해 주세요.

### 공통 규칙

- **토큰 단위**: 입력 + 캐시 읽기 + 캐시 쓰기 + 출력의 합입니다. `server.py`의 `vector()`가 만드는 네 항목의 합과 같고, `/api/state`의 `tokens` 합과도 같은 정의입니다.
- **시각 정렬**: 수집기가 실행 중인 컴퓨터의 지역 시각을 따릅니다. 분·시 경계, 자정(`day`), 월요일 자정(`week`)에 맞춥니다.
- **`null`과 `0`을 구분합니다**:
  - `coverage` 밖이거나, 그 도구의 기록을 읽을 수 없는 구간은 `null`입니다.
  - 기록이 있는데 쓰지 않은 구간은 `0`입니다.
  - 화면은 `null`을 빗금으로, `0`을 빈칸으로 그립니다.
- **`coverage`**: 출처별로 읽을 수 있었던 범위입니다. 화면 아래에 "기록 범위: 9월 3일부터 · 출처: Claude Code·Codex 대화 기록, 1top 수집기"처럼 표시합니다. 기록이 없는 도구(예: 대화 기록 파일이 없는 Aside)는 수집기 범위만 갖습니다.

### `series` (추이)

- `bins[i]`는 i번째 구간의 시작 시각(Unix 초)입니다.
  - 첫 구간은 `period`의 시작을 내림한 경계에서 시작합니다.
  - 마지막 구간은 진행 중이어도 됩니다.
  - `total`과 각 `tokens` 배열은 `bins`와 길이가 같습니다.
- **`by_model`**:
  - `key`는 보고된 모델 ID 원문입니다(`claude-opus-5-5`, `gpt-6-astra`, `glm-5.3`).
  - 한 세션이 중간에 모델을 바꾸면 메시지·턴 단위로 나눠서 셉니다.
  - 모델을 알 수 없으면 `key`를 `"unknown"`으로 합니다.
- **`by_project`**:
  - `key`는 세션 작업 폴더(`cwd`) 경로입니다.
  - `label`은 `sessions[].project`와 같은 규칙(`Path(cwd).name`)을 따릅니다.
  - 알 수 없으면 `key`를 `"unknown"`으로 합니다.
- **정렬과 합계**:
  - 두 목록 모두 기간 합계가 큰 순서로 상위 12개까지 보냅니다.
  - 나머지는 마지막 행 하나로 합칩니다: `{"key": "__other__", "folded": <합친 개수>, "tokens": [...]}`.
  - 이 컴퓨터는 작업 폴더가 750개가 넘어서, 전부 보내면 400구간 기준 응답이 2MB를 넘습니다.
  - 화면은 상위 5개와 "기타"로 다시 접습니다.
  - 각 구간에서 `sum(by_model) == sum(by_project) == total`이어야 합니다(`__other__` 포함).

### `heatmap` (히트맵, 기간 슬라이더와 별개)

- **`hours`**: 최근 30일(오늘 포함)의 모든 지역 시각 1시간 칸입니다. 형식은 `[날짜 "YYYY-MM-DD", 시(0-23), 토큰 | null]`이며 720행 안팎입니다.
- **`days`**: `coverage` 첫날부터 오늘까지의 모든 날짜입니다. 형식은 `["YYYY-MM-DD", 토큰 | null]`입니다.
- `period`와 `step`의 영향을 받지 않고 `kind`만 적용합니다. 기간을 바꿀 때마다 다시 계산하지 않도록 따로 캐시해 주세요.

## 과거 기록 가져오기

수집기 실행 이전 기록도 대화 기록 파일에서 채웁니다(사용자 결정, 2026-10-29). 메시지 내용은 저장하지 않고 시각·도구·모델·작업 폴더·토큰 수만 집계합니다.

- **Claude Code**: `~/.claude/projects/**/*.jsonl`(서브에이전트 기록 포함)을 읽습니다.
  - `type == "assistant"` 줄의 `timestamp`, `message.model`, `message.usage`, 그 줄의 `cwd`를 씁니다.
  - 한 응답이 여러 줄에 나뉘어 기록되고, 이어서 실행한 세션이 이전 메시지를 다시 담기도 합니다. 그래서 `message.id` + `requestId`로 전역에서 한 번만 셉니다.
  - `model == "<synthetic>"`은 제외합니다.
- **Codex**: `~/.codex/sessions/**/rollout-*.jsonl`을 읽습니다.
  - `event_msg.token_count`의 `info.total_token_usage` 누적값 차이를 씁니다. 지금 수집기의 `vector(codex=True)`와 감소를 초기화로 보는 규칙을 그대로 따릅니다.
  - 모델은 직전 `turn_context.model`, 작업 폴더는 `session_meta.cwd` 또는 `turn_context.cwd`입니다.
- **GLM 등 Claude Code 호환 도구**: Claude Code 규칙으로 읽고, `kind`는 수집기의 판정과 같게 둡니다.
- **두 번 세지 않습니다**: 수집기 `events`와 대화 기록이 겹치는 구간은 한쪽만 셉니다. 세션마다 수집기가 그 세션을 기록하기 시작한 시점 이전만 대화 기록에서 채우는 방식을 권합니다. 구체적인 방법은 백엔드에서 정해 주세요.
- **앞으로의 기록에는 모델과 작업 폴더를 함께 저장해야 합니다**: 지금 `events` 테이블에는 `sid`·`kind`만 있습니다. `model` 열을 추가하거나, `sid`별 모델·작업 폴더 메타 테이블을 두는 방식이 있습니다.
- **성능**:
  - 처음 한 번 전체를 읽고, 이후에는 파일별 오프셋으로 이어서 읽습니다.
  - 이 컴퓨터의 기록은 Claude Code 14GB, Codex 9.4GB입니다. 첫 가져오기는 수집기 시작을 막지 않도록 백그라운드에서 돌리고, 진행 중에는 `coverage`가 늘어나게 해 주세요.

## 화면 동작 (참고)

- **추이**: 기간 슬라이더를 따릅니다. 화면이 보내는 `step`은 다음과 같습니다. 1개월을 고르면 첨부 예시처럼 일별 추이가 됩니다.

  | 기간 | `step` |
  |---|---|
  | 1시간 이하 | `60` |
  | 6시간 이하 | `300` |
  | 1일 이하 | `900` |
  | 7일 이하 | `3600` |
  | 120일 이하 | `day` |
  | 그 이상 | `week` |

- **히트맵**: 기간 슬라이더와 별개입니다. 월간은 `days`, 시간대별은 `hours`를 요일×시로 합산해서 그립니다.
- **API가 없을 때**(이전 수집기의 `404`): 이 세 패널만 "수집기 업데이트 후 표시됩니다" 상태가 되고, 다른 화면에는 영향이 없습니다.

## 검증해 주실 것

1. 수집기 구간에서 `series.total`의 합이 같은 기간 `/api/state` `period_usage.windows[].tokens`의 합과 일치해야 합니다(허용 오차 0).

3. 대화 기록 구간에서 표본 세션 하나를 골라, 수동으로 계산한 합과 일치하는지 확인합니다. 이어서 실행한 세션의 중복 메시지도 포함해서 확인합니다.
4. `coverage` 밖은 `null`, 안의 미사용 구간은 `0`인지 테스트합니다.
5. `step` 경계가 지역 자정·정시에 맞는지 확인합니다(구간 400개 초과 시 `400` 포함).
